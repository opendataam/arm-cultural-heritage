## 0. Как читать документ

Структура документа опирается на ГОСТ 34.602-2020, но адаптирована для веб-портала. Разделы 1–4 описывают цели и содержание, разделы 5–11 — функциональные требования, раздел 12 — нефункциональные, разделы 13–15 — правовые вопросы, этапы и открытые вопросы. Приложения содержат перечень источников, сопоставление полей, перечень фасетов, языки, глоссарий и обоснование выбора архитектуры.

Обозначение этапов:

- требование без пометки обязательно для этапа 1 (MVP);
- **[Э2]** — обязательно для этапа 2;

Слова «должен» и «обязан» означают обязательное требование, «следует» — рекомендацию, отступление от которой Исполнитель обосновывает письменно.

## 2. Назначение и цели

### 2.1. Назначение

Портал собирает в одном месте описания и цифровые копии объектов армянского культурного наследия, которые хранятся в сотнях учреждений по всему миру. Портал не заменяет источники: он агрегирует метаданные, показывает цифровые объекты и ведёт пользователя к первоисточнику.

### 2.2. Цели

1. Дать единую точку поиска по армянскому наследию, рассеянному по музеям, библиотекам и архивам разных стран.
2. Сделать наследие доступным на языках Армении и диаспоры (раздел 8).
3. Связать разрозненные описания через общие сущности: персоны, места, организации, понятия, периоды.
4. Предоставить открытые данные и API для исследователей, разработчиков и учреждений.
5. Обеспечить повторное использование материалов в рамках их правового статуса.
6. Сохранить сведения о наследии, находящемся под угрозой утраты или вне доступа, включая утраченные и разрушенные объекты.

### 2.3. Целевые аудитории

| Аудитория | Основные задачи |
| --- | --- |
| Широкая аудитория в Армении и диаспоре | Знакомство с наследием, поиск семейной и локальной истории, выставки и истории |
| Исследователи (историки, искусствоведы, филологи, арменисты) | Расширенный поиск, полные метаданные, цитирование, выгрузки, IIIF |
| Преподаватели и учащиеся | Тематические подборки, материалы для уроков, свободные для использования изображения |
| Учреждения-партнёры | Публикация своих коллекций, статистика, обратная связь по качеству данных |
| Разработчики и дата-журналисты | API, массовые выгрузки, связанные открытые данные |
| Креативные индустрии и СМИ | Поиск материалов, разрешённых к повторному использованию |

### 2.4. Показатели успеха

Целевые значения утверждаются Заказчиком на этапе 0. Портал должен автоматически считать следующие показатели:

- число опубликованных записей, источников и учреждений-поставщиков;
- доля записей с цифровым объектом (изображение, текст, 3D, аудио, видео);
- доля записей со свободными правами (CC0, PDM, CC BY, CC BY-SA);
- доля записей, связанных хотя бы с одной сущностью из контролируемого словаря;
- доля записей с метаданными или переводом на каждом языке интерфейса;
- посещаемость по языкам и странам, глубина просмотра, доля успешных поисков (с переходом в карточку);
- число обращений к API и скачиваний выгрузок.

### 2.5. Границы проекта

В объём работ не входят:

- оцифровка фондов учреждений (Портал работает с уже оцифрованными материалами; модуль приёма данных от партнёров предусмотрен в разделе 11.8);
- юридическое урегулирование прав с каждым источником (выполняет Заказчик; Исполнитель предоставляет инструменты учёта прав, раздел 13);
- создание научных каталогов и экспертная атрибуция объектов;
- функции долговременного архивного хранения по модели OAIS (Портал хранит неизменяемые снимки собранных данных и локальные копии медиа, раздел 12.10, но не является архивом-хранилищем).

## 4. Содержание портала

### 4.1. Определение армянского культурного наследия

Запись включается в Портал, если выполняется хотя бы один критерий. Каждой записи присваивается список выполненных критериев: он используется как фасет и объясняет пользователю, почему объект находится на Портале.

| Код | Критерий | Пример |
| --- | --- | --- |
| `creator` | Создатель — армянин, армянская община или армянская организация | Картина Айвазовского; издание армянской типографии в Венеции |
| `place` | Объект создан или найден на территории исторической или современной Армении либо в местах армянских общин | Урартская бронза из Кармир-Блура; изделие мастеров Джульфы |
| `subject` | Объект изображает или описывает Армению, армян, армянскую историю или культуру | Фотография Еревана 1920-х годов; карта Армянского нагорья |
| `language` | Объект содержит текст на армянском языке или армянском письме | Рукопись; армяно-кипчакский документ армянским письмом |
| `holding` | Объект хранится в армянском учреждении | Фонды Национальной галереи Армении |

Критерий `holding` включается по решению Заказчика, так как он добавляет объекты, не связанные с армянской культурой по содержанию.

Объекты, отобранные автоматически, получают статус релевантности:

- **подтверждено** — сильные признаки в содержательных полях или ручное подтверждение куратором;
- **кандидат** — неоднозначные признаки; по умолчанию не показывается в публичной выдаче и попадает в очередь проверки (раздел 11.4);
- **отклонено** — исключено куратором; запись сохраняется во внутренней базе, чтобы не возвращаться в очередь при повторном сборе.

Для Госкаталога этим статусам соответствуют поля `armenia_decision`, `armenia_match_reasons` и связанные поля текущих выгрузок.

### 4.2. Типы объектов и цифровых материалов

Портал различает **тип цифрового материала** (что видит пользователь) и **тип объекта** (что описано). Пример: монета — тип объекта «нумизматика», тип материала «изображение».

Типы цифрового материала:

| Тип | Примеры | Основные форматы |
| --- | --- | --- |
| Изображение | Живопись, графика, фотографии, предметы | JPEG, TIFF, JPEG 2000, PNG, WebP; IIIF Image API |
| Текст | Книги, периодика, рукописи, документы, письма | Многостраничные IIIF-манифесты, PDF, ALTO/hOCR, TEI, EPUB |
| 3D | Хачкары, архитектура, археология, скульптура | glTF 2.0/GLB (выдача), OBJ, PLY, STL, FBX (исходные), облака точек LAS/LAZ, E57, 3D Tiles |
| Аудио | Народная музыка, записи на пластинках, устная история | MP3, AAC, Opus, FLAC, WAV; HLS |
| Видео | Кинохроника, фильмы, интервью | MP4 (H.264/H.265), WebM; HLS/DASH |
| Карта | Исторические карты, планы | IIIF + геореференсинг, GeoTIFF |
| Панорама | Сферические панорамы, виртуальные туры | Эквидистантные JPEG, многоуровневые тайлы |
| Набор данных | Каталоги, реестры, эпиграфические корпуса | CSV, JSON, Parquet, RDF |
| Веб-архив | Сайты армянских организаций и СМИ | WARC/WACZ |
| Только метаданные | Описания без цифровой копии, в том числе утраченных объектов | — |

Типы объектов берутся из классификаций источников и сводятся к контролируемому словарю Портала. Словарь связывается с Getty AAT, где это возможно.

### 4.3. Источники данных

Источники делятся на группы. Подробный предварительный перечень приведён в приложении А; доступность, условия использования и технический способ получения данных по каждому источнику уточняются на этапе 0.

1. **Российские государственные ресурсы**: Госкаталог Музейного фонда РФ, НЭБ, Президентская библиотека, крупные библиотеки и музеи.
2. **Армянские национальные ресурсы**: Матенадаран, Национальная библиотека Армении, Пан-армянская цифровая библиотека, государственная база движимого культурного наследия, музеи и архивы Армении.
3. **Учреждения диаспоры**: мхитаристские конгрегации, библиотеки и музеи армянских общин, исследовательские институты.
4. **Международные агрегаторы**: Europeana, DPLA, Trove, Deutsche Digitale Bibliothek, Wikimedia Commons, Wikidata, Internet Archive, HathiTrust.
5. **Мировые музеи и библиотеки с армянскими коллекциями**: Библиотека Конгресса, Национальная библиотека Франции, Британская библиотека, Бодлианская библиотека, Ватиканская библиотека, музеи с открытыми API.
6. **Специализированные ресурсы**: архитектура и памятники, 3D-модели, звукозаписи, фотоархивы, мониторинг наследия под угрозой.

### 4.4. Оценка объёмов

Объёмы уточняются на этапе 0 по результатам обследования источников. Исходные ориентиры:

- Госкаталог: 58 291 подтверждённая запись и 86 714 кандидатов;
- Пан-армянская цифровая библиотека: по открытым публикациям — более 253 тыс. цифровых объектов;
- Europeana, НЭБ и международные источники: определяются пробными запросами на этапе 0.

Архитектура должна рассчитываться на рост:

| Показатель | Этап 1 | Через 3 года | Проектный предел без смены архитектуры |
| --- | --- | --- | --- |
| Записи метаданных | 0,5 млн | 5 млн | 20 млн |
| Страницы и изображения (IIIF canvas) | 5 млн | 50 млн | 200 млн |
| Локально хранимые медиа | 10 ТБ | 100 ТБ | 500 ТБ |
| Полнотекстовый индекс | 1 млн страниц | 20 млн страниц | 100 млн страниц |

### 4.5. Принцип хранения: агрегатор и локальные копии

Портал работает по гибридной модели.

- **Агрегация по ссылке** (по умолчанию, как в Europeana). Портал хранит метаданные, превью и ссылки на цифровой объект у источника. Полноразмерные медиа отдаются с серверов источника — через IIIF или прямые ссылки.
- **Локальное хранение.** Портал хранит полноразмерные копии, если источник не предоставляет стабильного доступа, права позволяют хранение, объект находится под угрозой исчезновения из сети или если нужна обработка (OCR, конвертация 3D, транскодирование). Решение по каждому источнику фиксируется в реестре источников (раздел 6.1).

## 5. Требования к системе в целом

### 5.1. Архитектура

Портал состоит из слабосвязанных подсистем с документированными интерфейсами.

```text
                 ┌──────────────────────────────────────────────┐
  Источники ───► │ Подсистема агрегации                          │
  (API, OAI-PMH, │ коннекторы → сырые снимки → преобразование →  │
  IIIF, дампы,   │ нормализация → релевантность → обогащение →   │
  загрузка)      │ дедупликация → оценка качества                │
                 └───────────────┬──────────────────────────────┘
                                 ▼
  ┌──────────────┐   ┌──────────────────────┐   ┌─────────────────┐
  │ Обработка    │──►│ Хранилище записей    │──►│ Поисковый индекс│
  │ медиа: IIIF, │   │ (версии, provenance) │   │ (полный текст,  │
  │ OCR, 3D, AV  │   └──────────┬───────────┘   │ фасеты, гео)    │
  └──────────────┘              │               └────────┬────────┘
                                ▼                        ▼
                 ┌───────────────────────────────────────────────┐
                 │ API-слой: REST, IIIF, OAI-PMH, SPARQL [Э3]     │
                 └───────┬──────────────────────┬────────────────┘
                         ▼                      ▼
             ┌──────────────────────┐  ┌────────────────────────┐
             │ Публичный сайт (SSR) │  │ Административная часть │
             │ + CMS-контент        │  │ и кабинет партнёра     │
             └──────────────────────┘  └────────────────────────┘
```

Требования:

1. Публичный сайт должен получать данные только через API-слой. Тот же API доступен внешним разработчикам (раздел 10).
2. Подсистема агрегации должна работать независимо от публичного сайта: сбой сбора данных не влияет на доступность Портала.
3. Сырые данные источников хранятся неизменяемыми снимками. Любую опубликованную запись можно пересобрать из снимка и версии правил преобразования.
4. Все компоненты разворачиваются из кода инфраструктуры (IaC) и контейнеров. Отдельные окружения: разработка, тестирование, промышленная эксплуатация.
5. Конвейер агрегации управляется оркестратором (раздел 5.5). Массовая обработка медиа выполняется через очередь задач.

### 5.2. Открытость и выбор архитектуры

1. Исходный код, созданный по договору, передаётся Заказчику и публикуется под открытой лицензией (MIT, как и этот репозиторий, или иной по решению Заказчика).
2. Следует использовать открытые стандарты и открытое ПО. Использование проприетарных компонентов допускается только с письменного согласия Заказчика и при наличии плана замены.
3. Портал создаётся как компонентная сборка вокруг собственного ядра: конвейер, хранилище записей, поиск, API, публичный сайт. Готовые платформы-агрегаторы (Finna и VuFind, стек Europeana, Blacklight, Supplejack) целиком не разворачиваются и не форкаются. Обоснование и сравнение вариантов — в приложении Е.
4. Открытые компоненты подключаются как библиотеки или отдельные сервисы (раздел 5.4). Компоненты под копилефт-лицензиями (GPL, AGPL, EUPL) подключаются только как самостоятельные сервисы, без копирования их кода в собственный код Портала и без объединения с ним в одну сборку. Так собственный код остаётся под выбранной лицензией. Спорные случаи решает юрист Заказчика.
5. Решения аналогов используются как образцы: UX и композиция страниц портала Europeana (portal.js), маппинги DPLA ingestion3 и Rikolti, модули валидации EDM Europeana Metis.

### 5.5. Требования к оркестрации конвейера

1. Оркестратор — открытое ПО, которое разворачивается на инфраструктуре Заказчика без обязательных платных сервисов.
2. Конвейер описывается как граф наборов данных (активов): каждая стадия раздела 6.3 — набор с явными зависимостями. Оркестратор показывает происхождение наборов.
3. Каждый источник из реестра (раздел 6.1) — отдельная партиция со своим расписанием. Добавление источника в реестр не требует изменения кода оркестрации. Сбой одной партиции не влияет на остальные.
4. Повторы выполняются с экспоненциальной задержкой. Параллельность ограничивается по источникам и типам задач.
5. Можно перезапустить часть графа и выполнить бэкфилл по выбранным источникам и периодам.
6. Метаданные каждого прогона (объёмы, контрольные суммы, версии правил, время) сохраняются и доступны в интерфейсе и через API.
7. Проверки качества данных встроены в конвейер. Нарушение критической проверки блокирует публикацию. Пример: объём записей источника упал более чем на 30%.
8. Запуск выполняется по расписанию и по событию: появление нового дампа, оповещение IIIF Change Discovery.
9. О сбоях и проваленных проверках кураторы оповещаются по электронной почте и в мессенджере.
10. Коннекторы и преобразования реализуются как функции и консольные команды, не зависящие от оркестратора, с собственными тестами. Код оркестрации — тонкий слой над ними. Цель — заменить оркестратор без переписывания конвейера.
11. Массовые мелкие операции (обработка отдельных изображений, страниц, файлов) выполняются пакетами в очереди задач, которые запускает оркестратор. Отдельные записи и файлы не моделируются как задачи или партиции оркестратора.
12. Прерванный сбор продолжается с места остановки: коннектор сохраняет курсор или `resumptionToken` OAI-PMH.
13. Происхождение отдельной записи (раздел 6.11) хранится в хранилище записей. Оркестратор отвечает за происхождение наборов.
14. Интерфейс оркестратора недоступен из интернета без VPN или прокси с единым входом (раздел 12.4).

Рекомендуемый Dagster (Apache-2.0) удовлетворяет этим требованиям. В открытой версии авторизация обеспечивается прокси (п. 14), а оповещения — сенсорами (п. 9). Требованиям также удовлетворяет Apache Airflow 3. Окончательный выбор делается на этапе 0 по результатам прототипа конвейера на 2–3 источниках и с учётом опыта команды Исполнителя.

## 6. Подсистема агрегации данных

### 6.1. Реестр источников

Для каждого источника хранится карточка:

- наименование на языках Портала, страна, тип учреждения, сайт, контакт;
- правовая основа: соглашение, открытая лицензия или публичные условия; ссылка на документ; дата проверки;
- технический способ получения данных, адрес точки доступа, формат, расписание обновления;
- версия правил сопоставления полей;
- модель хранения медиа: по ссылке или локально (раздел 4.5);
- правила отбора (весь источник, отбор по запросу, отбор классификатором релевантности);
- ответственный куратор, статус (активен, приостановлен, архивный);
- статистика: записей собрано, опубликовано, отклонено, ошибок, дата последнего успешного сбора.

### 6.2. Коннекторы

Портал должен поддерживать следующие способы получения данных:

| Способ | Форматы и протоколы |
| --- | --- |
| OAI-PMH | Dublin Core, EDM, MARC21/MARCXML, MODS, METS, LIDO, EAD |
| REST API | JSON, XML; авторизация по ключу; постраничная выдача курсором |
| IIIF | Presentation API 2.1 и 3.0, IIIF Collections, Change Discovery API 1.0 |
| SRU и Z39.50 | MARC, Dublin Core |
| SPARQL | Wikidata и другие RDF-ресурсы |
| Файловые выгрузки | CSV, JSON, JSON Lines, XML, Parquet, RDF (Turtle, N-Triples, JSON-LD) |
| Загрузка партнёром | Шаблон CSV/XLSX, EDM XML, LIDO, MARC; через кабинет партнёра (раздел 11.8) |
| Сбор со страниц | HTML-разметка, sitemap, schema.org. Только при отсутствии API, с соблюдением `robots.txt`, условий сайта и ограничений частоты запросов |

Требования к коннекторам:

1. Коннектор поддерживает полный и инкрементный сбор, а также обнаружение удалённых записей.
2. Коннектор ограничивает частоту запросов и повторяет их с экспоненциальной задержкой. Параметры задаются в реестре источников.
3. Сбой одного коннектора не останавливает остальные.
4. Добавление коннектора типового протокола выполняется настройкой без программирования. Для нестандартного источника разрабатывается плагин по документированному интерфейсу.

### 6.3. Конвейер обработки

Каждая запись проходит стадии в указанном порядке. Результат каждой стадии сохраняется с журналом.

1. **Сбор.** Сырой ответ источника сохраняется неизменяемым снимком с датой, контрольной суммой SHA-256 и параметрами запроса.
2. **Преобразование.** Поля источника сопоставляются с моделью данных Портала (раздел 6.4) по версионируемым правилам.
3. **Нормализация.** Даты, языки, места, типы, права и единицы измерения приводятся к стандартам (раздел 6.5).
4. **Определение релевантности.** Для источников, не посвящённых целиком армянской тематике, запись классифицируется по критериям раздела 4.1 (раздел 6.6).
5. **Обогащение.** Связывание с сущностями и внешними словарями, геокодирование, машинный перевод (раздел 6.7).
6. **Дедупликация и группировка** (раздел 6.8).
7. **Оценка качества.** Расчёт уровней качества и проверка ссылок (раздел 6.9).
8. **Публикация.** Индексация и обновление API. Записи со статусом «кандидат» и записи ниже минимального уровня качества не публикуются автоматически.

Конвейер должен:

- перезапускаться с любой стадии для отдельной записи, источника или всего корпуса;
- выполнять пробный прогон без публикации и показывать отчёт о различиях с текущей версией;
- формировать отчёт о каждом прогоне: число записей на входе и выходе каждой стадии, ошибки, время, контрольные суммы входных данных и версии правил (по образцу текущего `output/goskatalog/report.json`).

### 6.4. Модель данных

Внутренняя модель должна быть совместима с Europeana Data Model (EDM): это позволяет обмениваться данными с Europeana и другими агрегаторами. Расширения EDM допускаются и документируются.

Основные классы:

| Класс | Назначение |
| --- | --- |
| Культурный объект (`edm:ProvidedCHO`) | Описываемый объект: рукопись, картина, здание, запись песни |
| Агрегация (`ore:Aggregation`) | Описание объекта конкретным источником: права, поставщик, ссылки |
| Цифровой ресурс (`edm:WebResource`) | Файл или сервис: изображение, IIIF-манифест, 3D-модель, видео |
| Персона, организация (`edm:Agent`, `foaf:Organization`) | Создатели, изображённые лица, владельцы, учреждения |
| Место (`edm:Place`) | Место создания, находки, изображения, хранения |
| Период (`edm:TimeSpan`) | Даты и исторические периоды |
| Понятие (`skos:Concept`) | Типы объектов, техники, материалы, темы |
| Событие [Э2] | Экспедиции, выставки, перемещения объектов (провенанс) |

Обязательные элементы опубликованной записи:

- постоянный идентификатор Портала и идентификатор записи у источника;
- название хотя бы на одном языке с языковой меткой;
- тип цифрового материала и тип объекта;
- поставщик данных и учреждение-держатель;
- правовой статус цифрового объекта по контролируемому списку (раздел 13.1);
- ссылка на запись у источника или цифровой объект;
- критерии и статус релевантности (раздел 4.1);
- происхождение записи: источник, дата сбора, версия правил.

Рекомендуемые элементы: описание, создатели и их роли, даты создания (исходная строка и нормализованный интервал), места, техника и материалы, размеры, инвентарный номер, провенанс, язык текста, связанные объекты, части и целое.

Иерархия и связи:

- запись может иметь части (книга — страницы, альбом — фотографии, фонд — дела) и входить в целое;
- связи между записями типизированы: «копия», «фрагмент», «изображение того же объекта», «то же издание», «перевод».

Для 3D-объектов дополнительно хранятся: метод создания (фотограмметрия, лазерное сканирование, моделирование), дата съёмки, число полигонов, уровни детализации, наличие текстур, масштаб и система координат, сведения о реконструкции и использованных источниках (парадата по Лондонской хартии).

### 6.5. Нормализация

| Аспект | Требование |
| --- | --- |
| Даты | Исходная строка сохраняется. Нормализованное значение — EDTF (ISO 8601-2) с интервалом «от–до» в годах для фасета и шкалы времени. Поддерживаются неточные даты («ок. 1650», «XIII в.», «2-я пол. XIX в.») на всех языках источников, даты до нашей эры и даты по армянскому летоисчислению (раздел 8.3) |
| Языки | Коды BCP 47. Различаются восточноармянский (`hy`), западноармянский (`hyw`) и древнеармянский грабар (`xcl`), если это указано источником или определено автоматически |
| Письменность | Коды ISO 15924 (`Armn`, `Cyrl`, `Latn`, `Arab`, `Geor`, `Grek` и др.). Учитывается армянское письмо для неармянских языков (например, армяно-кипчакский, армяно-турецкий) |
| Места | Связь с контролируемым словарём мест (раздел 6.7); координаты WGS 84; исторические и современные названия с периодами действия |
| Типы и техники | Сведение к словарю Портала со связью с Getty AAT |
| Права | Сведение к контролируемому списку (раздел 13.1). Если права не указаны, присваивается статус «Права не определены» |
| Размеры и вес | Значение, единица (СИ), измерение (высота, ширина, глубина, диаметр, вес); исходная строка сохраняется |
| Текст | Unicode NFC для хранения. Нормализация для поиска — раздел 8.3. Удаление HTML и управляющих символов с сохранением абзацев |

### 6.6. Определение релевантности

1. Используется сопоставитель с учётом полей и реестр терминов, разработанные для Госкаталога (`scripts/matcher.py`, `data/terms.csv`). Исполнитель встраивает их в конвейер или заменяет решением с не худшими показателями на размеченной выборке.
2. Реестр терминов редактируется через административную часть с проверкой по схеме `schema/terms.schema.json` и историей изменений.
3. Каждое решение классификатора сопровождается объяснением: найденные термины, поля, причины (аналог полей `armenia_matched_*` и `armenia_match_reasons`).
4. Классификатор оценивается на размеченной выборке. Отчёт о точности и полноте формируется при каждом изменении реестра или правил. Метрики относятся только к выборке, и это указывается в отчёте.
5. **[Э2]** Следует добавить модель машинного обучения как дополнительный признак для записей-кандидатов. Модель не заменяет правила и ручную проверку, а её вклад в решение отражается в объяснении.

### 6.7. Обогащение и связывание

1. **Сущности.** Портал ведёт собственный словарь сущностей (персоны, организации, места, понятия, периоды) со стабильными идентификаторами. Начальное наполнение — сущности реестра терминов (`entity_id`) и Wikidata.
2. **Внешние идентификаторы.** Сущности связываются с Wikidata, VIAF, ISNI, GND, LCNAF, авторитетными файлами Национальной библиотеки Армении, Getty ULAN, AAT и TGN, GeoNames, Pleiades (для античных мест).
3. **Автоматическое связывание** выполняется с оценкой уверенности. Связи ниже порога уверенности попадают в очередь проверки и не публикуются.
4. **Варианты имён.** Для каждой сущности хранятся формы на всех языках и в разных системах транслитерации. Пример: Хачатурян, Khachaturian, Khatchadourian, Khatchatourian, Jachaturián, Խաչատրյան, Խաչատուրեան.
5. **Геокодирование.** Текстовые места преобразуются в ссылки на словарь мест. Исторические названия связываются с современными (раздел 13.4).
6. **Машинный перевод** названий и описаний на языки интерфейса — раздел 8.4.
7. **[Э2]** Распознавание именованных сущностей в описаниях и полных текстах.
8. **[Э3]** Автоматическая разметка изображений (типы объектов, цвета, похожие изображения). Результат помечается как машинный и не смешивается с данными источника.

Все обогащения хранятся отдельно от данных источника, с указанием способа получения (источник, автоматически, вручную) и могут быть отозваны.

### 6.8. Дедупликация и группировка

Один объект может быть описан несколькими источниками: рукопись — в каталоге хранилища, в Europeana и на Wikimedia Commons; книга — в НЭБ и в Национальной библиотеке Армении.

1. Портал выявляет вероятные дубликаты по идентификаторам (инвентарные номера, шифры рукописей, ISBN, OCLC, внешние URI), совпадению метаданных и перцептивному хешу изображений.
2. Подтверждённые дубликаты объединяются в кластер. Пользователь видит одну основную карточку и блок «Этот объект в других источниках». Записи источников не изменяются и остаются доступны.
3. Для печатных изданий применяется группировка «произведение — издание — экземпляр» (по модели IFLA LRM): несколько цифровых копий одного издания показываются вместе.
4. Объединение и разделение кластеров выполняется куратором вручную с журналом изменений.

### 6.9. Уровни качества

По образцу Europeana Publishing Framework каждой записи присваиваются два уровня.

**Уровень содержания (0–3):**

| Уровень | Условие |
| --- | --- |
| 0 | Только метаданные, нет цифрового объекта или превью |
| 1 | Есть превью или цифровой объект низкого разрешения (менее 0,95 Мпикс для изображений) |
| 2 | Цифровой объект пригоден для просмотра (изображения от 0,95 Мпикс, полный текст, проигрываемые аудио, видео, 3D) |
| 3 | Высокое качество (изображения от 4 Мпикс или IIIF с глубоким масштабированием) и права, разрешающие повторное использование |

**Уровень метаданных (A–C):** зависит от полноты обязательных и рекомендуемых элементов, наличия языковых меток и числа связей с контролируемыми словарями. Методика расчёта утверждается на этапе 0.

Уровни используются для ранжирования, фильтров и отчётов партнёрам. Записи уровня 0 публикуются и находятся поиском, но по умолчанию ранжируются ниже. Пользователь может отключить их фильтром «Только с цифровым объектом».

Проверка ссылок: Портал не реже одного раза в месяц проверяет доступность ссылок на цифровые объекты и записи источников. Недоступные ресурсы помечаются, а отчёт передаётся куратору источника.

### 6.10. Обработка медиа

1. **Превью.** Для каждой записи с изображением формируются превью нескольких размеров в форматах WebP и JPEG.
2. **IIIF.** Для локально хранимых изображений Портал предоставляет IIIF Image API 3.0. Для каждой записи с цифровым объектом формируется манифест IIIF Presentation 3.0, в том числе для внешних изображений без собственного манифеста.
3. **OCR и HTR.** Для текстов без текстового слоя выполняется распознавание: печатный текст — Tesseract (модели `hye`, `rus`, `eng`, `fra` и др.) или аналог; рукописи и старопечатные армянские книги — специализированные модели (Kraken, Transkribus, Calfa или аналоги) **[Э2]**. Результат хранится в ALTO XML с координатами слов и показывается в просмотрщике как текстовый слой. Качество распознавания оценивается на выборке, а машинный текст помечается.
4. **3D.** Исходные модели конвертируются в glTF 2.0/GLB со сжатием геометрии (Draco или meshopt) и текстур (KTX2), формируется несколько уровней детализации и превью-изображение. Облака точек конвертируются в формат потоковой загрузки (Potree или 3D Tiles). **[Э2]**
5. **Аудио и видео.** Транскодирование в HLS с несколькими битрейтами, формирование превью-кадра и волновой формы. Поддерживаются субтитры и расшифровки (WebVTT). **[Э2]**
6. **Контроль целостности.** Для локально хранимых файлов хранятся контрольные суммы SHA-256 и выполняется периодическая проверка.

### 6.11. Обновление, удаление, версионность

1. Каждая опубликованная запись имеет историю версий. Изменения у источника отражаются при следующем сборе.
2. Запись, удалённая у источника, снимается с публикации. Её постоянный идентификатор продолжает работать и показывает страницу «Запись больше не доступна у источника» со ссылкой на поставщика и, если права позволяют, с последними метаданными.
3. Происхождение данных описывается по модели W3C PROV: какой снимок, какая версия правил и какие обогащения дали текущее состояние записи.

## 7. Публичный интерфейс

### 7.1. Общие требования

1. Интерфейс по композиции и сценариям сопоставим с Europeana (раздел 3). Визуальная идентичность разрабатывается отдельно и отражает армянскую культурную традицию без стилизации «под старину» в ущерб читаемости.
2. Дизайн-система (типографика, цвета, компоненты, сетка, иконки) оформляется как библиотека компонентов с документацией.
3. Адаптивная вёрстка: от 320 px (телефон) до 2560 px; приоритет мобильной версии.
4. Шрифты поддерживают армянское, кириллическое, латинское, арабское, грузинское и греческое письмо с согласованной метрикой (например, семейство Noto; для армянского — также GHEA Grapalat или другой шрифт по решению дизайнера). Шрифты подключаются с сервера Портала.
5. Светлая и тёмная темы **[Э2]**.
6. Все страницы имеют постоянные понятные URL с языковым префиксом: `/{язык}/item/{id}`, `/{язык}/search?...`.
7. Состояние поиска (запрос, фасеты, сортировка, страница, вид) полностью отражается в URL.

### 7.3. Главная страница

- показатели Портала: число объектов, учреждений, стран, языков;
- блок партнёров.

### 7.4. Поиск

**Простой поиск**

1. Одна строка поиска на всех страницах.
2. Автодополнение: подсказки запросов, сущностей (персоны, места, понятия с типом и изображением) и коллекций на языке интерфейса.
3. Поиск без учёта регистра, диакритики, вариантов орфографии и транслитерации (раздел 8.3).
4. Межъязыковой поиск: запрос раскрывается через многоязычные названия сущностей (раздел 8.5).
5. Исправление опечаток («Возможно, вы искали…»).
6. Время ответа — раздел 12.1.

**Расширенный поиск**

1. Поиск по полям: название, описание, создатель, место, дата, тип, учреждение, инвентарный номер, полный текст.
2. Логические операторы (И, ИЛИ, НЕ), фразы в кавычках, маски `*` и `?`, близость слов.
3. Конструктор запроса в интерфейсе для пользователей без знания синтаксиса.
4. Поиск по полному тексту с подсветкой фрагментов и переходом на страницу документа.
5. **[Э3]** Поиск по изображению: загрузка изображения или «найти похожие».
6. **[Э3]** Семантический поиск на многоязычных векторных представлениях. Дополняет, но не заменяет точный поиск; пользователь видит, какой режим применён.

**Выдача**

1. Виды: сетка (по умолчанию), список, карта **[Э2]**, шкала времени **[Э2]**.
2. Карточка в выдаче: превью, название на языке интерфейса (с пометкой о машинном переводе), создатель, дата, учреждение, значки типа материала и прав.
3. Сортировка: релевантность, дата создания (по возрастанию и убыванию), дата добавления, название.
4. Постраничная навигация и выбор числа результатов. Глубокая выдача — курсором в API.
5. Число результатов по каждому значению фасета.
6. Сохранение поиска и подписка на новые результаты **[Э2]**.
7. Пустая выдача предлагает ослабить фильтры, исправленный запрос или связанные сущности.

**Фасеты** (полный перечень — приложение В): тип цифрового материала, тип объекта, коллекция, период и годы (ползунок и гистограмма), место (с картой), создатель, учреждение, страна учреждения, источник, язык текста, техника и материал, права использования, наличие полного текста, наличие IIIF, уровень качества, критерии релевантности.

### 7.5. Карточка объекта

1. **Просмотрщик** по типу материала (раздел 7.6) — в верхней части страницы, с полноэкранным режимом.
2. **Основная информация:** название, создатель, дата, учреждение, краткое описание.
3. **Языки метаданных:** исходный язык показывается всегда. Переключатель «Показать перевод» выводит машинный перевод на язык интерфейса с явной пометкой и ссылкой на исходный текст.
4. **Полные метаданные:** все поля в группах «Описание», «Создание», «Физические характеристики», «Провенанс», «Идентификаторы», «Права», «Источник записи».
5. **Сущности:** персоны, места, понятия, периоды — ссылки на страницы сущностей.
6. **Права и использование:** значок и текстовое пояснение правового статуса, что можно делать с объектом, требования к указанию авторства.
7. **Скачивание** в доступных размерах и форматах, если права и источник позволяют. Подпись для указания авторства генерируется автоматически.
8. **Цитирование:** форматы ГОСТ Р 7.0.100-2018, Chicago, APA, MLA, BibTeX, RIS, CSL-JSON.
9. **IIIF:** ссылка на манифест, перетаскиваемый значок IIIF, кнопка «Открыть в Mirador».
10. **Поделиться:** копирование постоянной ссылки, отправка в соцсети и мессенджеры.
11. **Переход к источнику:** заметная ссылка «Смотреть на сайте учреждения».
12. **Связанные объекты:** части и целое, тот же объект в других источниках (раздел 6.8), похожие объекты (по сущностям, а в Э3 — по изображению).
13. **Сообщить об ошибке:** форма с выбором типа ошибки (метаданные, права, нерелевантный объект, нарушение прав, недоступная ссылка). Обращение попадает к куратору источника.
14. **Происхождение записи:** источник, дата сбора и обновления, ссылка на исходную запись, история версий **[Э2]**.
15. **Предупреждение о чувствительном содержании** (раздел 13.3), если оно назначено.
16. Разметка schema.org (раздел 12.7).

### 7.6. Просмотрщики

**Изображения**

- IIIF-просмотрщик (Mirador 3 или Universal Viewer, либо собственный на основе OpenSeadragon): глубокое масштабирование, поворот, полноэкранный режим, многостраничные объекты, миниатюры;
- сравнение двух изображений рядом, в том числе из разных записей **[Э2]**;
- для изображений без IIIF — простой просмотр с масштабированием.

**Книги, рукописи, документы**

- постраничное листание, режим разворота, переход к странице, оглавление (если есть в манифесте);
- поиск по тексту документа (IIIF Content Search API) с подсветкой на изображении страницы;
- переключение «изображение / распознанный текст / изображение с текстовым слоем»;
- скачивание PDF или отдельных страниц, если права позволяют;
- для рукописей — показ структуры (листы recto/verso, миниатюры, колофоны), если она есть в данных источника.

**3D-объекты [Э2]**

- веб-просмотрщик glTF (`<model-viewer>`, three.js или 3DHOP): вращение, масштаб, панорамирование, освещение, режим без текстур, измерение расстояний, аннотированные точки;
- облака точек и крупные сцены — Potree или CesiumJS;
- прогрессивная загрузка: сначала лёгкая версия модели, затем детализированная;
- работа на мобильных устройствах; режим дополненной реальности на поддерживающих устройствах **[Э3]**;
- для моделей, размещённых на внешних платформах (например, Sketchfab), — встроенный проигрыватель платформы и ссылка на источник;
- поддержка 3D в будущей версии IIIF Presentation по мере её стандартизации **[Э3]**.

**Аудио и видео [Э2]**

- проигрыватель с потоковой загрузкой, субтитрами и синхронизированной расшифровкой;
- переход к фрагменту по ссылке с временной меткой;
- поддержка IIIF AV-манифестов.

**Карты [Э2]**

- исторические карты в IIIF-просмотрщике;
- наложение геореференцированной карты на современную подложку с регулировкой прозрачности (расширение IIIF Georeference или аналог).

**Панорамы [Э3]**: просмотр сферических панорам и переходов между точками.

**Веб-архивы [Э3]**: воспроизведение WARC/WACZ (например, ReplayWeb.page).

**Наборы данных [Э2]**: предпросмотр таблицы, описание полей, скачивание.

Все просмотрщики должны быть доступны с клавиатуры и экранных дикторов (раздел 12.6).

### 7.7. Страницы сущностей

**Персона:** имя на языке интерфейса и варианты, годы жизни, портрет, краткая биография (из Wikidata или от редактора, с указанием источника), роли (создатель, изображённое лицо, владелец), объекты, связанные персоны и места, внешние идентификаторы.

**Место:** названия во времени (раздел 13.4), карта, тип (город, монастырь, область, археологический памятник), объекты, созданные, найденные или изображающие место, вложенность (село — область — историческая область), статус памятника и ссылки на реестры наследия, если применимо.

**Организация:** учреждение-держатель или иная организация, история, объекты, коллекции.

**Понятие:** техника, материал, тип объекта, тема; определение, связанные понятия, объекты.

**Период:** хронологические рамки, описание, объекты, связанные места и персоны.

Каждая страница сущности содержит встроенную выдачу с фасетами и ссылку «Все объекты в поиске».

### 7.8. Тематические коллекции

Коллекция — сохранённый поисковый запрос, ручная подборка или их сочетание, с вводным текстом и обложкой. Начальный список утверждается Заказчиком. Пример:

- Рукописи и миниатюра; Старопечатная книга; Периодика;
- Архитектура и памятники; Хачкары;
- Ковры и текстиль; Ювелирное искусство и металл; Керамика;
- Живопись и графика; Фотография; Кино;
- Музыка и звукозаписи;
- Археология; Нумизматика;
- Этнография и народный костюм;
- Армянские общины мира;
- Геноцид армян и историческая память;
- Утраченное и находящееся под угрозой наследие.

### 7.9. Истории и виртуальные выставки

1. **Истории** — статьи с текстом, встроенными объектами Портала, цитатами и галереями. Создаются в CMS.
2. **[Э2] Виртуальные выставки** — многостраничные повествования с разделами, полноэкранными изображениями, сменой сцен при прокрутке, картами и шкалой времени.
3. Каждая история и выставка существует на одном или нескольких языках. Если перевода нет, пользователь видит доступные языковые версии.
4. Встроенный объект всегда ссылается на свою карточку и показывает правовой статус.

### 7.10. Пользовательские галереи [Э2]

- пользователь собирает объекты в галереи с названием и описанием;
- галерея бывает личной, доступной по ссылке или публичной (публичные галереи проходят модерацию);
- редакторы публикуют избранные галереи;
- экспорт галереи в CSV и IIIF Collection.

### 7.11. Страницы учреждений и источников

Название, описание, логотип, страна, ссылка на сайт, число объектов, распределение по типам и периодам, коллекции учреждения, источники, через которые получены данные, дата последнего обновления.

### 7.12. Карта и шкала времени [Э2]

1. **Карта:** кластеры объектов по местам создания, находки и изображения; фильтры как в поиске; переключение подложек, включая исторические карты. Технология — MapLibre GL или аналог с векторными тайлами.
2. **Шкала времени:** распределение объектов по годам с масштабированием от тысячелетий до десятилетий; выбор интервала фильтрует выдачу.

### 7.13. Информационные страницы

«О проекте», «Партнёрам» (как передать данные), «Правила использования», «Заявление о доступности», «Политика конфиденциальности», «Контакты», «FAQ», «Документация API», «Открытые данные». Все страницы редактируются в CMS на всех языках интерфейса.

### 8.2. Требования к локализации интерфейса

1. Все строки интерфейса вынесены в ресурсы локализации. Строки в коде недопустимы, что проверяется автоматически при сборке.
2. Формат сообщений — ICU MessageFormat с правилами множественного числа CLDR (в русском и украинском — 4 категории CLDR с учётом дробных чисел, в арабском — 6).
3. Даты, числа и списки форматируются по данным CLDR для каждого языка. Если данные CLDR для языка неполны (проверить для `hyw`), Исполнитель готовит собственные данные локали.
4. **Двунаправленный текст.** Для арабского и персидского интерфейс зеркалируется. Вёрстка использует логические свойства CSS (`margin-inline-start` и т. п.). Фрагменты на другом направлении письма (армянские имена в арабском интерфейсе, номера, коды) изолируются (`<bdi>`, `dir="auto"`).
5. Каждый элемент с текстом на языке, отличном от языка страницы, имеет атрибут `lang`. Это нужно для правильного выбора шрифта, переносов и синтеза речи экранными дикторами.
6. Язык выбирается так: явный выбор пользователя (сохраняется в cookie и профиле) → язык из URL → заголовок `Accept-Language` при первом визите. Автоматическое перенаправление по геолокации запрещено.
7. Переключатель языков доступен на каждой странице. Языки в нём названы на собственных языках: Հայերեն, Русский, English, Français, Español, Արեւմտահայերէն, العربية, ქართული, Українська, Deutsch, فارسی, Português, Ελληνικά, Türkçe и т. д.
8. При переключении языка пользователь остаётся на той же странице.
9. Редакционный контент без перевода на выбранный язык показывается на языке по умолчанию с уведомлением и списком доступных переводов. Цепочка языков по умолчанию настраивается (например, `hyw` → `hy` → `en`; `uk` → `ru` → `en` — по решению Заказчика).
10. Длина строк в интерфейсе рассчитывается на рост текста при переводе до 40%. Вёрстка проверяется на самом длинном языке.

### 8.3. Особенности армянского языка

1. **Две литературные нормы.** Восточноармянский (`hy`) и западноармянский (`hyw`) — отдельные языки интерфейса с отдельными переводами, а не автоматическая конвертация.
2. **Две орфографии.** Реформированная (советская, принятая в Армении) и классическая (месроповская, принятая в западной диаспоре и у армян Ирана). Поиск должен находить слово в любой орфографии независимо от орфографии запроса. Пример: Երևան, Երեւան; թյուն, թիւն; յա, եա. Таблица соответствий утверждается с лингвистом-консультантом. **[Э3]** Режим показа восточноармянского интерфейса в классической орфографии.
3. **Лигатура «և».** Символ U+0587 при поиске эквивалентен последовательностям «եւ» и «եվ».
4. **Армянская пунктуация** (՝ ՛ ՜ ՞ ։ ՚ « ») учитывается при токенизации: вопросительный и восклицательный знаки внутри слова не разрывают его.
5. **Морфология.** Применяется стеммер армянского языка (Snowball; в OpenSearch и Solr есть анализатор `armenian`). Качество стемминга проверяется на тестовом наборе запросов.
6. **Транслитерация.** Поиск латиницей и кириллицей находит армянские записи и наоборот. Поддерживаются системы ISO 9985, ALA-LC, Hübschmann-Meillet, BGN/PCGN, бытовая латинская транслитерация и русская практическая транскрипция. Учитывается разница восточного и западного произношения: Petrosyan и Bedrossian, Tigran и Dikran, Gevorg и Kevork.
7. **Ввод.** Поле поиска имеет экранную армянскую клавиатуру и транслитерационный ввод (латинский набор автоматически превращается в армянский текст), так как у многих пользователей диаспоры нет армянской раскладки.
8. **Армянское летоисчисление.** Даты в колофонах рукописей и ранних изданий записаны по армянскому летоисчислению (эпоха — 552 год н. э.) армянскими буквенными цифрами (например, ՌՃԺԵ). Портал хранит исходную запись, переводит дату в юлианский или григорианский календарь и показывает обе формы.
9. **Армянские цифры** распознаются в номерах томов, листов и годах при наличии таких данных у источника.
10. **Грабар** (`xcl`) поддерживается как язык метаданных и текста документов, но не как язык интерфейса.

### 8.4. Многоязычные метаданные

1. Каждое текстовое значение хранится с языковой меткой. Исходные значения источника никогда не перезаписываются.
2. Названия сущностей, типов, техник и материалов выводятся на языке интерфейса из контролируемых словарей и Wikidata.
3. Названия и описания объектов переводятся машинно на языки интерфейса этапа 1; для этапов 2 и 3 — по мере подключения языков. Машинный перевод:
   - всегда помечается как машинный, с названием системы перевода;
   - показывается рядом с оригиналом или по переключателю;
   - индексируется для поиска с меньшим весом, чем исходный текст;
   - хранится с версией модели и датой и может быть пересчитан.
4. Качество машинного перевода для каждой языковой пары оценивается на выборке до включения. Пара с неприемлемым качеством не публикуется. Особое внимание уделяется армянскому, так как качество массовых систем перевода для него ниже, чем для крупных европейских языков.
5. **[Э2]** Пользователи и редакторы могут предложить ручной перевод метаданных. После модерации ручной перевод заменяет машинный и помечается как ручной.

### 8.5. Межъязыковой поиск

1. Запрос сопоставляется с названиями сущностей на всех языках. Если запрос однозначно указывает на сущность, поиск выполняется также по её идентификатору и всем её вариантам. Пример: запрос «Комитас» находит Komitas, Gomidas, Կոմիտաս.
2. Если сопоставление неоднозначно, пользователь видит подсказку с выбором сущности.
3. Поиск выполняется по исходным текстам и по машинным переводам.
4. В выдаче указывается, по какому варианту найдено совпадение.

### 8.6. Процесс перевода

1. Строки интерфейса переводятся в Weblate (или аналоге) с памятью переводов и глоссарием терминов Портала.
2. Перевод на каждый язык выполняет профессиональный переводчик — носитель языка. Второй носитель проверяет перевод в контексте страниц до публикации. Западноармянский перевод выполняет носитель западноармянского языка.
3. Машинный перевод строк интерфейса без проверки человеком не допускается.
4. Новые строки не попадают в промышленную среду, пока не переведены на все обязательные языки. Для дополнительных языков допускается временный показ на языке по умолчанию.
5. Глоссарий ключевых терминов (типы объектов, права, названия разделов) утверждается Заказчиком для каждого языка.

## 9. Личный кабинет и участие пользователей [Э2]

1. **Регистрация и вход:** по электронной почте с подтверждением; вход через внешних провайдеров (набор утверждает Заказчик с учётом доступности сервисов в странах целевых аудиторий). Двухфакторная аутентификация для ролей с правами редактирования.
2. **Функции:** избранное, галереи (раздел 7.10), сохранённые поиски с уведомлениями, история просмотров (отключаемая), языковые настройки, экспорт и удаление своих данных.
3. **[Э3] Краудсорсинг:** расшифровка рукописных документов, исправление OCR, определение людей и мест на фотографиях, перевод метаданных, теги. Каждый вклад проходит модерацию или многоступенчатую проверку и хранится отдельно от данных источника с указанием автора. Учреждению-источнику передаётся отчёт о вкладах.
4. **[Э3] Семейные архивы:** сбор семейных фотографий, документов и воспоминаний диаспоры (по образцу проекта Europeana 1914–1918), включая организацию выездных «дней сбора». Загружаемые материалы проходят модерацию, автор выбирает лицензию и подтверждает права. Персональные данные третьих лиц — раздел 12.5.

## 10. API и открытые данные

1. **REST API** (документация OpenAPI 3.1):
   - поиск с фасетами, курсорной пагинацией и выбором профиля полей;
   - получение записи в форматах JSON-LD (EDM), EDM RDF/XML, schema.org JSON-LD;
   - получение сущностей и автодополнение;
   - сведения об источниках и учреждениях;
   - **[Э2]** аннотации (W3C Web Annotation).
2. **IIIF:** Presentation API 3.0 (манифесты и коллекции), Image API 3.0 для локальных изображений, Content Search API для полных текстов **[Э2]**, Change Discovery API для оповещения внешних агрегаторов **[Э2]**.
3. **OAI-PMH** для выдачи метаданных в EDM и Dublin Core внешним агрегаторам. В частности, Портал может передавать армянские материалы в Europeana в роли агрегатора, если Заказчик примет такое решение **[Э2]**.
4. **Массовые выгрузки:** полный набор опубликованных метаданных в JSON Lines и Parquet, обновление не реже одного раза в месяц, с описанием схемы, контрольными суммами и журналом изменений.
5. **[Э3] Связанные открытые данные:** публикация записей и сущностей в RDF, разрешаемые URI сущностей, точка доступа SPARQL.
6. **Лицензия метаданных:** метаданные, созданные Порталом (нормализация, обогащения, словари), публикуются под CC0. Метаданные источников публикуются на условиях источника; ограничения указываются в выдаче API.
7. **Доступ:** чтение без ключа с ограничением частоты; бесплатный ключ для повышенных лимитов; страница статистики использования для владельца ключа.
8. **Стабильность:** версионирование API в URL, уведомление пользователей не менее чем за 6 месяцев до прекращения поддержки версии.
9. **Встраивание:** код для встраивания карточки объекта и галереи на сторонние сайты **[Э2]**.

Права настраиваются на уровне ролей и, при необходимости, отдельных источников или языков. Все действия в административной части записываются в журнал аудита.

### 11.2. Управление источниками

- карточки источников (раздел 6.1), включение и выключение, расписание;
- редактор правил сопоставления полей с предпросмотром результата на выборке записей;
- таблицы соответствия значений (например, классификация источника → типы Портала);
- запуск сбора и обработки вручную, просмотр журнала, отчёт о различиях перед публикацией.

### 11.3. Мониторинг конвейера

- панель состояния: последние прогоны, ошибки, время, объёмы по стадиям;
- оповещения кураторам о сбоях, резком изменении объёма (например, источник вернул на 30% меньше записей) и росте числа недоступных ссылок;
- отчёты о качестве данных по источникам: уровни, полнота полей, доля связанных сущностей.

Панель строится на данных оркестратора (раздел 5.5) и хранилища записей. Кураторам не требуется работать в интерфейсе оркестратора.

### 11.4. Очередь проверки релевантности

Очередь нужна для ручной проверки записей-кандидатов: только по Госкаталогу их 86 714.

1. Список кандидатов с фильтрами по источнику, найденным терминам, полям, типу объекта, учреждению.
2. Карточка проверки: превью, ключевые поля, подсветка найденных терминов, причины решения классификатора.
3. Решения: «подтвердить», «отклонить», «отложить» с комментарием. Массовые действия над отфильтрованной группой с подтверждением.
4. Горячие клавиши для быстрой проверки.
5. Решения куратора сохраняются при повторных сборах и используются как размеченные данные для оценки классификатора.
6. Двойная проверка выборки решений (настраиваемый процент) и отчёт о согласованности кураторов.

### 11.5. Управление сущностями

- создание, редактирование, объединение и разделение сущностей с журналом;
- проверка автоматических связей ниже порога уверенности;
- привязка к Wikidata и другим словарям, импорт названий и описаний;
- **[Э2]** передача новых сущностей в Wikidata с согласия Заказчика.

### 11.6. Редакционная CMS

- коллекции, истории, выставки, главная страница, информационные страницы, меню;
- встраивание объектов Портала по идентификатору или через поиск в редакторе;
- черновики, предпросмотр, публикация по расписанию, история версий;
- языковые версии каждого материала со статусом перевода;
- библиотека медиа для редакционных изображений с учётом прав.

### 11.7. Обращения пользователей

- очередь сообщений об ошибках из карточек объектов (раздел 7.5) с маршрутизацией к куратору источника или юристу;
- обработка обращений о нарушении прав и запросов на удаление (раздел 13.2) с контролем сроков;
- шаблоны ответов на всех языках интерфейса.

### 11.8. Кабинет партнёра [Э2]

- загрузка данных по шаблону (CSV/XLSX с инструкцией на языках Портала, EDM XML, LIDO, MARC) с автоматической проверкой и отчётом об ошибках до публикации;
- регистрация точки доступа OAI-PMH, IIIF или API для регулярного сбора;
- статистика: число объектов, просмотры, скачивания, переходы на сайт учреждения, запросы, по которым находили объекты;
- отчёт о качестве данных с рекомендациями по улучшению;
- исправления и сообщения пользователей по объектам учреждения.

### 11.9. Статистика

- посещаемость, поиски, просмотры объектов, скачивания, переходы к источникам — по языкам, странам, источникам, коллекциям;
- запросы с пустой выдачей (для улучшения словарей и транслитерации);
- показатели раздела 2.4;
- инструмент — самостоятельно размещённая система веб-аналитики без передачи данных третьим лицам (Matomo, Plausible или аналог).

1. Соответствие OWASP ASVS уровня 2.
2. Только HTTPS (TLS 1.2 и выше), HSTS, политика безопасности контента (CSP), защита от CSRF и XSS.

4. Разделение сетей: административная часть, конвейер и интерфейс оркестратора недоступны из интернета без VPN или прокси с единым входом.
5. Секреты хранятся в специализированном хранилище, а не в коде и конфигурации.
6. Зависимости проверяются на уязвимости при каждой сборке.
7. Независимое тестирование на проникновение перед запуском каждого этапа.
8. Журналы безопасности хранятся не менее 1 года.

### 12.5. Персональные данные

1. Обработка персональных данных пользователей соответствует законодательству страны размещения и стран основных аудиторий: Закону Республики Армения «О защите персональных данных», GDPR (для пользователей и партнёров из ЕС) и иному применимому законодательству по заключению юриста Заказчика.
2. Сбор данных минимален. Аналитика по умолчанию работает без cookie или с согласием пользователя. Баннер согласия предлагает отказ от необязательных cookie так же просто, как согласие.
3. Пользователь может выгрузить и удалить свои данные.
4. Метаданные объектов могут содержать персональные данные (имена на фотографиях, архивные документы XX века, свидетельства). Для источников с такими данными юрист Заказчика определяет правила публикации, а Портал поддерживает скрытие отдельных полей и записей.

### 12.6. Доступность для людей с инвалидностью

1. Соответствие WCAG 2.2 уровня AA на всех языках интерфейса.
2. Полное управление с клавиатуры, видимый фокус, пропуск навигации, правильная структура заголовков и ориентиров.
3. Альтернативный текст для изображений: из метаданных (название, описание) или, для редакционных изображений, заданный редактором.
4. Совместимость с NVDA, JAWS, VoiceOver и TalkBack. Проверяется в том числе чтение армянского и арабского текста.
5. Контрастность, масштабирование до 200% без потери функций, уважение настройки «уменьшить движение».
6. Независимый аудит доступности перед запуском и публикация заявления о доступности.

### 12.7. Поисковая оптимизация

1. Серверный рендеринг всех публичных страниц.
2. Разметка schema.org в JSON-LD: `CreativeWork` и подтипы (`VisualArtwork`, `Photograph`, `Book`, `Manuscript`, `Map`, `3DModel`, `MusicRecording`, `Movie`, `Dataset`, `ArchiveComponent`), `Person`, `Place`, `Organization`, `Collection`.
3. Атрибуты `hreflang` для всех языковых версий, канонические URL, многоязычные карты сайта с разбивкой по типам страниц.
4. Open Graph и разметка карточек соцсетей с превью изображения.
5. Страницы выдачи с фасетами закрыты от индексации, кроме избранных посадочных страниц.

### 12.8. Совместимость

- две последние версии Chrome, Edge, Firefox, Safari; Safari iOS и Chrome Android двух последних основных версий ОС;
- работа основных функций (поиск, карточка, просмотр изображения) при медленном соединении 3G;
- просмотрщики 3D и видео работают при отсутствии WebGL2 или кодеков в упрощённом режиме (превью и ссылка на скачивание).

### 12.9. Размещение и доступность из разных стран

1. Страна и площадка размещения определяются Заказчиком с учётом законодательства о персональных данных, санкционных ограничений и доступности из стран целевых аудиторий.
2. До запуска проверяется доступность Портала и CDN из Армении, России, Грузии, Ирана, Ливана, Сирии, стран ЕС, США, Аргентины. Выбирается конфигурация, не блокируемая в этих странах, либо предусматриваются зеркала.
3. Внешние сервисы (шрифты, аналитика, карты, видео) подключаются с серверов Портала или через прокси, чтобы блокировка одного сервиса не ломала страницу.

### 12.10. Постоянство и сохранность

1. У каждой записи, сущности, коллекции и выставки есть постоянный идентификатор, который не меняется при обновлении данных и смене технологий. Рекомендуется ARK (бесплатная регистрация NAAN); альтернатива — Handle или DOI.
2. Постоянные ссылки продолжают работать после удаления записи (раздел 6.11).
3. Сырые снимки источников, локальные копии медиа и решения кураторов хранятся с контрольными суммами, в двух географически разнесённых хранилищах.

### 12.11. Мониторинг и эксплуатация

- метрики (Prometheus, Grafana или аналоги), централизованные журналы, отслеживание ошибок (Sentry или аналог);
- внешний мониторинг доступности из нескольких стран;
- автоматическое тестирование и развёртывание (CI/CD); выпуск без простоя;
- руководство администратора и регламент эксплуатации.

### 12.12. Качество кода и документация

1. Автоматические тесты: модульные, интеграционные, сквозные для ключевых сценариев. Покрытие кода конвейера данных — не менее 80%.
2. Тестовые наборы для армянской нормализации, транслитерации и поиска с эталонными результатами.
3. Документация: архитектура, модель данных, правила сопоставления по каждому источнику, API (OpenAPI), руководства пользователя, редактора, куратора, администратора и партнёра.
4. Документация пользователя переводится на языки интерфейса этапа 1; техническая — на русский и английский.

## 13. Правовые и этические требования

### 13.1. Правовой статус материалов

1. Каждый цифровой объект имеет правовой статус из контролируемого списка: лицензии Creative Commons (CC0, CC BY, CC BY-SA, CC BY-NC, CC BY-NC-SA, CC BY-ND, CC BY-NC-ND), Public Domain Mark и заявления RightsStatements.org (12 заявлений, включая «Охраняется авторским правом», «Не охраняется», «Статус не определён»).
2. Правовой статус назначает источник. Портал не меняет его самостоятельно; исправление выполняется по согласованию с источником или по решению юриста Заказчика с записью в журнале.
3. Правовой статус метаданных и цифрового объекта хранится раздельно.
4. В интерфейсе статусы сводятся в три группы для фильтра: «Можно использовать свободно», «Можно использовать с условиями», «Использование ограничено или не определено».
5. Скачивание полноразмерных файлов доступно только при статусе, допускающем его, и если источник не запрещает скачивание.
6. Для каждого источника хранится правовая основа использования его данных (раздел 6.1). Источник без подтверждённой правовой основы не публикуется.

### 13.2. Обращения о нарушении прав

1. Процедура уведомления и удаления: форма на каждой карточке и отдельный адрес для обращений.
2. Срок первичного ответа — не более 5 рабочих дней. Спорный материал на время рассмотрения может быть скрыт по решению юриста.
3. Все обращения и решения регистрируются.

### 13.3. Чувствительный контент

1. Предупреждения и размытие превью (с раскрытием по действию пользователя) для изображений насилия, в том числе фотографий периода Геноцида армян, а также останков людей.
2. Редакционная политика для религиозных и сакральных объектов, человеческих останков и материалов о живых людях утверждается Заказчиком до запуска.
3. Тексты к материалам о трагических событиях готовят и проверяют профильные специалисты.

### 13.4. Политика топонимики

Значительная часть армянского наследия связана с территориями, которые сейчас находятся в разных государствах. Названия многих мест менялись.

1. Для каждого места хранятся все известные названия с языком, периодом употребления и статусом: историческое, современное официальное, современное употребимое в армянской традиции.
2. На странице места и в карточке объекта показываются историческое название, относящееся ко времени создания объекта, и современное название с указанием страны.
3. Правила выбора основного названия на каждом языке интерфейса закрепляются в редакционной политике, которую утверждает Заказчик до запуска этапа 1.
4. Поиск находит место по любому из названий.

### 13.5. Использование искусственного интеллекта

1. Любые данные, полученные автоматически (машинный перевод, OCR и HTR, автоматические связи, теги, тексты), помечаются в интерфейсе и API.
2. Сгенерированные тексты не публикуются как редакционные без проверки человеком.
3. Отправка метаданных и медиа внешним сервисам ИИ допускается только при совместимости с правами и условиями источника.

## Приложение Е. Обоснование выбора архитектуры

Сведения о лицензиях, стеке и активности проектов проверены по их репозиториям на GitHub на 2026-11-01.

### Е.1. Рассмотренные варианты

- **Вариант А** — ядро на основе VuFind и RecordManager (подход Finna) с доработками.
- **Вариант Б** — компонентная сборка вокруг собственного ядра. **Выбран.**

Причины выбора варианта Б:

1. ТЗ требует модели EDM и страниц сущностей: персон, мест, понятий, периодов (разделы 6.4, 7.7). В VuFind запись — плоский библиотечный документ, а сущности ограничены авторитетными записями персон и организаций.
2. Большинство источников (приложение А) отдают данные через REST API и IIIF. RecordManager поддерживает сбор по OAI-PMH, HTTP-файлам, SFX, Sierra API и GeniePlus. Коннекторы к остальным источникам пришлось бы писать в любом варианте.
3. Армянская нормализация, межъязыковой поиск и машинный перевод метаданных (раздел 8) требуют собственной схемы индекса. В варианте А их пришлось бы переносить как доработки при каждом обновлении VuFind.
4. Имеющийся код (экстрактор, сопоставитель, реестр терминов) написан на Python. Вариант Б сохраняет один язык для конвейера и API.
5. Собственный код остаётся под выбранной лицензией. Код, производный от VuFind, был бы под GPL-2.0.

Цена выбора: поиск, карточки объектов и личный кабинет, которые в варианте А были бы готовыми, разрабатываются самостоятельно. Это учитывается в сроках этапа 1.

### Е.3. Оркестратор

| Вариант | Сильные стороны | Ограничения |
| --- | --- | --- |
| Dagster (рекомендуется) | Модель активов и происхождение наборов; динамические партиции по источникам; проверки качества; метаданные прогонов в интерфейсе; Python; Apache-2.0 | Не предназначен для миллионов мелких задач. В открытой версии нет авторизации интерфейса. Часть функций есть только в платном Dagster+ (встроенные оповещения, окружения для веток). Сообщество меньше, чем у Airflow |
| Apache Airflow 3 (альтернатива) | Самое большое сообщество; в версии 3 есть активы и версии DAG | Модель построена вокруг задач. Тяжелее в эксплуатации и локальной разработке |
| Prefect | Гибкие динамические потоки | Слабее модель активов и происхождение данных |
| Temporal | Надёжное выполнение очень долгих процессов | Не ориентирован на данные: нет каталога наборов и их происхождения |
| Argo Workflows | Работает нативно в Kubernetes | Конвейер описывается в YAML, а не в Python |
| cron и скрипты | Простота; подходит для прототипа | При десятках источников с зависимостями, повторами и мониторингом пришлось бы писать собственный оркестратор |

Требования раздела 5.5 сформулированы так, чтобы им удовлетворяли и Dagster, и Airflow 3.
